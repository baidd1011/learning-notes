# Vibe Coding 的项目上下文如何组织与维护

> 发布日期：2026-10-05 · 最近核对：2026-10-05

用 AI 开发项目时，我们通常会经历多个会话：从搭建基础结构，到实现功能，再到排查问题和调整设计。随着功能增加，一个问题会越来越明显：新会话如何快速理解项目，又如何知道上一个会话做到了哪里？

我们采用的方式，是把跨会话需要的信息保存在仓库中，让不同文档承担不同职责。聊天用于讨论当前任务；讨论形成的需求、决策和进度，在需要后续使用时写入对应文档。新会话通过这些文档、当前代码和 Git 状态恢复上下文。

下面介绍这套文档架构，以及开发过程中如何维护它。目录与内容是组织方式的示例，可以根据项目规模调整。

## 一、我们的文档架构

```text
project/
├── AGENTS.md
├── README.md
├── docs/
│   ├── requirements.md
│   ├── architecture.md
│   ├── database.md
│   ├── api.md
│   ├── decisions/
│   │   └── 001-data-retention.md
│   └── tasks/
│       ├── 001-project-setup.md
│       ├── 002-feature-development.md
│       └── 003-search-pagination.md
├── backend/
└── frontend/
```

这套结构把项目上下文分成四类：长期开发规则、项目知识、具体任务状态，以及实际实现。文档之间通过路径建立联系，各自维护自己的内容。

| 载体 | 回答的问题 | 主要内容 |
|---|---|---|
| `AGENTS.md` | Agent 应该怎么工作？ | 开发约定、验证要求、文档入口 |
| `README.md` | 这是什么项目，如何使用？ | 项目概况、环境、运行与检查方式 |
| `docs/` 中的专题文档 | 系统有哪些规则，如何设计？ | 需求、架构、数据模型、接口 |
| `docs/decisions/` | 为什么采用这个设计？ | 重要选择、原因和影响 |
| `docs/tasks/` | 这次任务做到哪里？ | 目标、计划、进度、验证、下一步 |
| 代码、测试与 Git | 当前实现是什么？ | 可执行行为、约束及变更历史 |

小项目可以合并专题文档。例如，只有两张表时，可以先把数据模型写在 `architecture.md` 中；内容增长后再拆出 `database.md`。文件数量应该随项目复杂度增长。

### AGENTS.md：精简的规则与上下文入口

`AGENTS.md` 保存跨任务有效的开发约定。例如，项目可以约定：后端业务逻辑放在 service 层，数据库结构变化必须提供迁移，修改业务规则后需要验证相关异常路径。

它还负责告诉 Agent 在什么情况下读取哪个文档：

```markdown
## 文档入口
- 项目概况与运行方式：README.md。
- 实现或修改业务规则：docs/requirements.md。
- 修改模块职责或依赖关系：docs/architecture.md。
- 修改数据模型：docs/database.md。
- 修改接口与前后端对接：docs/api.md。
- 开始或继续任务：读取对应 docs/tasks 文件。

## 完成要求
- 核对当前代码与任务记录，保留已有用户修改。
- 更新受本次变更影响的文档。
- 记录实际验证结果；未验证的内容明确标注。
- 长期开发规则变化时维护本文件。
```

这样，新会话首先获得少量稳定规则，再按任务需要读取细节。分页任务需要查看列表接口、查询代码和相关任务记录；它通常不需要同时读取全部设计决策。

Codex 的官方说明指出，它会在启动时发现并组合适用的 `AGENTS.md`，具体受工作目录和指令文件层级影响。因此，我们把项目入口放在根目录，并保持内容精简。[官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

### README 与专题文档：保存项目知识

`README.md` 面向开发者，提供理解和运行项目所需的入口。它应该说明项目的用途、当前支持的功能、如何启动、如何执行检查，以及哪些能力仍未完成。

专题文档描述更具体的项目约定：

- `requirements.md`：功能范围、业务规则、边界条件与验收标准。
- `architecture.md`：前端页面、API、service 和数据库之间的职责与调用关系。
- `database.md`：数据实体、字段、唯一约束、关联关系和迁移方式。
- `api.md`：请求参数、响应结构、分页含义和错误约定。

这些文档应分别保存各自负责的信息。例如，数据删除规则在需求文档中定义；数据库文档说明如何保证关联数据的一致性；接口文档说明删除失败时如何响应。三者描述同一规则在不同层面的表现，避免到处复制整段说明。

### decisions：保存重要设计的原因

代码可以说明数据删除如何实现，但未必能说明为什么选择这个行为。

假设我们讨论过物理删除和逻辑删除两种方案，最终选择逻辑删除，是为了满足误操作恢复和历史追溯的需求。这个原因可以记录在 `001-data-retention.md` 中。

一条决策记录只需要讲清楚背景、选择、原因和影响。普通变量命名、按钮颜色等细节无需单独记录。后续设计改变时，补充新的决定并标明旧决定已被替代，保留可理解的演变过程。

### tasks：保存具体任务的执行状态

任务文件连接计划与实施。以 `003-search-pagination.md` 为例，它应让新会话知道：本次搜索支持哪些条件，分页接口如何设计，哪些部分已经实现，哪些检查尚未完成。

建议包含以下内容：

```markdown
# 搜索与分页

## 目标与范围
支持关键词搜索、条件筛选与分页，明确组合条件的行为和边界。

## 实现计划
查询接口、前端筛选、分页状态与相关验证。

## 当前进度
分别记录已实现、已验证和未完成的部分。

## 决策与发现
记录影响后续工作的选择，以及实施中发现的差异。

## 验证结果
记录检查方式、实际结果及尚未验证的场景。

## 下一步
明确后续第一个动作、相关文件和验收条件。
```

任务文件只保存对继续工作有帮助的信息。例如“后端组合筛选已验证，前端改变条件后尚未重置页码”，比一段完整聊天记录更容易用于接续。

对于更复杂的任务，可以增加 `.agent/PLANS.md`，统一规定计划的写法；每个具体任务仍保存在独立任务文件中。`PLANS.md` 的文件名本身不会触发自动更新，需要通过项目规则明确使用方式。这一组织方式借鉴了 OpenAI 的执行计划实践；相关 Cookbook 目前已标为归档。[Using PLANS.md for multi-hour problem solving](https://developers.openai.com/cookbook/articles/codex_exec_plans)

## 二、文档如何随开发维护

文档更新由项目变化触发。一次会话可能只更新任务记录，也可能同时涉及需求、数据库和接口。维护时先识别变化属于哪个层面，再修改对应文档。

### 开始任务：核对文档与实际项目

每次开始任务，先查看适用的开发规则、README、对应任务文件和相关源码，同时检查 Git 状态。

这一步的目的，是确认当前起点。任务文件可能写着“接口已完成”，但代码只有部分实现；README 也可能保留旧的启动命令。遇到差异时，结合需求、代码、测试和实际运行核实原因，再修正文档或实现。

已有行为并不自动代表正确需求。若代码允许重复标识，而需求要求唯一，应该修复实现，不能仅为匹配代码就删掉需求约束。

### 实施过程中：及时记录关键变化

不必每改一行代码就更新文档。适合记录的时机包括：确定影响后续工作的方案、完成一个可验证阶段、发现原计划不成立，以及遇到需要交接的阻塞。

例如，开发分页时发现前端把当前页记录数量当成总数。这时任务文件记录问题与修复进度，`api.md` 明确 `total` 表示筛选后的全部记录数量；如果没有改变长期开发规则，就不需要修改 `AGENTS.md`。

### 任务结束：让交接成为完成条件

完成一个功能，除了代码和检查结果，还需要让下一次会话能理解最终状态。

结束前核对：任务状态是否准确，接口与模型文档是否反映变更，README 中的运行方式是否仍有效，重要决策是否已经留下原因。文档与相关代码一同进入 Git，便于追踪。

尚未完成的任务也可以交接，但必须明确区分已实现、已验证和未完成。例如，分页查询测试通过，并不能证明前端快速切换条件时不会被旧响应覆盖。没有验证的场景继续保留为待验收项。

### 换会话：从仓库恢复工作

新会话的恢复路径可以很短：

```text
AGENTS.md → README → 对应任务文件 → 相关设计、源码与测试
```

用户只需要指出本次目标或任务文件。Agent 根据记录核对现状，再继续实施。

任务结束时已经留下结果和验证证据，可以直接开始下一个独立任务；任务做到一半时，则先把关键决策、当前问题和下一步写入任务文件。这样换会话不会要求重新解释整套项目背景。

## 三、哪些变化应该更新哪些文档

| 项目中的变化 | 需要维护的内容 |
|---|---|
| 新增业务字段 | 需求字段、数据模型与迁移、接口定义、任务记录 |
| 搜索新增筛选条件 | 搜索规则、接口参数、任务记录 |
| 修改启动端口或安装方式 | README；若 AGENTS 中也有相关约定，同步修正 |
| 调整 service 层职责 | 架构文档；长期开发约定改变时更新 AGENTS |
| 改变数据删除策略 | 需求、数据约束、接口行为、决策记录与任务状态 |
| 修复前端分页问题，接口未变 | 对应任务记录和验证结果 |
| 页面按钮颜色调整 | 通常无需修改架构或长期规则 |

`/init` 在这套流程中负责提供规则文件的起点。首次创建后，需要按项目实际情况审核；已有合适的 `AGENTS.md` 时，后续通过有针对性的修改维护它。官方也将 `/init` 描述为生成可进一步编辑并保存的规则草稿。[官方开发命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)

## 四、控制文档规模与可信度

项目持续开发后，文档最容易出现两个问题：相同信息多处复制，以及计划被写成既成事实。

我们为每类信息指定主要位置，在其他文档中通过路径引用。任务结束后，任务文件保留结果、验证和必要的历史；已经成为稳定项目知识的内容整理到专题文档中。

同时，为计划和结果保留明确标记。“准备采用分页接口”“接口已实现”“分页测试已通过”“浏览器流程已验收”是不同状态。只有留下实际验证结果，新会话才能知道哪些信息可以作为工作起点，哪些仍需检查。

这套架构的价值，在于让项目每完成一次开发，都留下可继续使用的上下文。长期规则保持精简，项目知识随实现更新，任务文件记录执行状态，代码与验证结果提供核对依据。会话可以更换，项目仍然能够接着推进。
